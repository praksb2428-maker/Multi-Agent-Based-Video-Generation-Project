# 프로젝트 작업 계획

새 개발 요청의 범위와 완료 기준을 정할 때 사용한다. 이 스킬은 앱 코드·테스트를 수정하거나 제작을 승인하지 않는다.

## 입력

사용자 요청, [제안서 원본](../../../Video_Production_Project.md), [프로젝트 규칙](../../../AGENTS.md), [브리프](../../../docs/project-brief.md), [결정 기록](../../../docs/decisions/README.md), 관련 현재 파일을 읽는다. `proposal.md`를 새로 복제하지 않고 사용자가 확정한 원본을 사용한다.

## 절차

1. 요청한 결과와 현재 구현을 비교하고 필요한 작업·제외 범위를 정한다. 개발 하네스의 작성·검토 역할과 서비스의 숏츠 제작 역할을 구분한다.
2. 파트별 책임·입출력, 변경 허용 파일, 의존 관계, 완료 기준과 검사 방법을 체크리스트로 적는다. 같은 회차의 작업 폴더와 현재 후보·검사 입력을 정한다. 기존 제작 코드·승인·원본 결과는 요청 없이 바꾸지 않는다.
3. 이미 확정한 결정을 재사용한다. 실제 모델, 유료 호출, 설치, 외부 전송, 공개·배포 등 중요한 결정이 없으면 없다고 적는다. 새 결정이 필요하면 적용 정책에 맞는 선택지와 근거를 제시하고 답변 전 의존 작업을 멈춘다.
4. [개발 흐름](../../../docs/workflow.md)에 따라 계획 → 작성 → 검증 → 검토 → 문서화 → 개인 최종 확인을 연결한다. 작성자는 허용된 후보와 change.md, 검증 담당은 checks.md, 별도 검토자는 review.md, 문서화 담당은 docs-update.md를 남긴다. 검사 실패는 작성자에게, 범위·중요 결정 변경은 계획 담당과 개인에게 돌린다. 필요한 검사·검토가 미완료면 보류한다. 작업 이름·역할·세션 변경으로 소진한 수리 한도를 초기화하지 않는다.

## 산출물

기본 기록은 `workspace/plan.md`다. 기존 기록이 있으면 새 회차 폴더를 정해 그 안에 plan.md를 저장하고 이전 기록을 보존한다. 요청·범위·영향 파일·담당·인계 경로·후보 식별·검사·미정·다음 단계를 담는다. 계획은 작성자에게 인계하고, 작성 후 `$project-check` 검증과 별도 검토를 거쳐 `$project-docs`로 연결한다. 이 스킬이 작성·검토 역할을 자동 실행하지는 않는다.

## 중단 조건

필수 입력·정책·현재 상태가 불명확하거나 권한·중요 결정이 없으면 영향 작업을 보류한다. 계획 작성은 기획 승인·제작 승인·실제 실행 허가가 아니다.
