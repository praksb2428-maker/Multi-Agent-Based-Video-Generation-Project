# 개인·AI 작업 흐름

이 문서는 **개발 작업 과정**의 기준이다. 목표와 현재 범위는 [프로젝트 브리프](project-brief.md), 중요한 선택은 [결정 기준](decisions/README.md), 검사는 [테스트 계획](testing.md)을 따른다. 제작 서비스의 역할과 승인 순서는 [아키텍처](architecture.md)에 있다. 개발 시에는 한 파일 집합의 작성자를 한 명으로 유지하고 중요한 구현은 별도 fresh 읽기 전용 검토로 확인한다. 이것은 제품의 LLM 에이전트팀 실행을 뜻하지 않는다.

## 단계와 책임

개발 역할의 흐름은 **계획 → 작성 → 검증 → 검토 → 문서화 → 개인 최종 확인**이다. 요청·범위 확인에는 [project-plan](../.agents/skills/project-plan/SKILL.md), 실제 검사에는 [project-check](../.agents/skills/project-check/SKILL.md), 확인된 결과 반영에는 [project-docs](../.agents/skills/project-docs/SKILL.md)를 사용한다. 작성과 검토는 아래 역할 지침을 따른다. 역할은 다섯 가지, 재사용 스킬은 세 개이며 새 에이전트 자동 호출기를 뜻하지 않는다.

진행 담당자는 현재 주 AI이며 개인의 결정에 따라 다음 단계를 연결한다. 같은 파일 집합의 작성자는 한 명으로 유지하고, 현재 단계·후보·남은 수리 횟수·보류 사유·다음 담당을 해당 작업 기록에 남긴다. 설계만으로 추가 에이전트·모델·도구 권한을 부여하지 않는다.

`workspace/plan.md` 등 기존 기록이 있으면 새 회차의 작업 폴더를 정한다. 이후 그 폴더의 `plan.md` → `change.md` → `checks.md` → `review.md` → `docs-update.md`를 인계하며 후보 파일/해시와 검사 입력을 연결한다. 이후 단계는 현재 회차·후보가 맞는지 확인한다. 과거 회차의 통과를 바뀐 후보의 통과로 쓰지 않는다. 스킬을 직접 읽어 수행했다면 그 방식과 자동 발견 미확인을 그대로 적는다. 서비스의 기획·제작 승인은 이 개발 절차의 통과와 별개다.

| 단계 | 개인 | AI의 입력 → 출력 |
| --- | --- | --- |
| 1. 요청 확인 | 목표·제약·원하는 결과를 제공한다. | 요청, 제안서, 기존 파일 → 현재 상태와 완료 조건을 확인한다. 추측한 구현을 사실로 쓰지 않는다. |
| 2. 영향과 계획 정리 | 범위가 맞는지 판단한다. | 계획 담당이 관련 파일·결정 기록을 읽고 → plan.md에 요구 ID·쓰기 허용 범위·담당·의존 순서·검사·미정을 정리한다. |
| 3. 중요 결정 확인 | [결정 기준](decisions/README.md)에 걸리는 선택을 확정하거나 보류한다. | 선택지·장단점·추천 이유·영향 → 개인에게 질문하고 답을 ADR에 기록한다. 답이 필요한 변경은 그 전까지 진행하지 않는다. |
| 4. 작업 | 필요한 범위·자료를 제공한다. | 작성자가 확정 계획 안에서 최소 변경을 적용하고 → change.md에 변경 파일·후보 해시·검사 대상·남은 항목을 남긴다. 원본·무관한 변경을 보존한다. |
| 5. 검사 | 필요한 경우 결과물을 직접 확인한다. | 검증 담당이 [테스트 계획](testing.md)에 따라 실행/재사용/미실행과 근거를 checks.md에 남긴다. 이어 검토자가 같은 후보·요구·diff·근거를 독립 점검해 review.md에 통과/수정 필요/판정 불가를 남긴다. 둘 다 소스·테스트를 고치지 않는다. |
| 6. 문서 갱신 | 설명과 실제 결과가 맞는지 본다. | 문서화 담당이 변경·검사·검토를 읽고 → 영향받는 문서와 docs-update.md를 갱신한다. 실패·보류도 기록하되 성공으로 바꾸지 않는다. 조건·권한·검사 기준을 바꾸면 계획과 영향 검증/검토로 돌아간다. |
| 7. 개인 채택 | 결과를 채택하거나 보완·보류를 지시한다. | 요구별 구현·검증/보류/제외/차단, 필수 검사·독립 검토·문서 링크 확인 결과와 남은 한계를 보고한다. 필수 항목 미확인은 완료로 쓰지 않는다. 개인 채택과 제품의 제작 승인을 대신하지 않는다. |

## 작성자와 검토자

| 역할 | 입력 | 출력 | 수정 범위 |
| --- | --- | --- | --- |
| 계획 담당(AI) | 개인 요청·제안서·현행 규칙·기존 결정 | plan.md: 범위·권한·검사·미정·회차 폴더 | 계획 기록만 쓴다. 앱 코드·테스트·미정 결정은 바꾸지 않는다. |
| 작성자(AI) | 유효한 plan.md·확정 ADR·관련 코드·문서 | 허용 범위의 후보, change.md: 파일·해시·영향·인계 | 계획의 허용 파일만 수정한다. 기준을 낮추거나 승인을 대행하지 않는다. 검증·검토 판정을 스스로 만들지 않는다. |
| 검증 담당(읽기 전용 AI) | 같은 후보·plan/change·테스트 기준·기존 실행 근거 | checks.md: 명령·종료·입력·실행/재사용/미실행 | 검사 실행과 자기 검사 기록만 쓴다. 앱 코드·테스트·요구 기준을 고치지 않는다. |
| 검토자(별도 문맥의 읽기 전용 AI) | 같은 후보·완료 조건·diff·checks·결정 기록 | review.md: 통과/수정 필요/판정 불가와 근거 | 작성에 참여하지 않고 자기 검토 보고서만 쓴다. 차단 결함과 선택 개선을 구분해 작성자 또는 계획 담당에게 넘긴다. |
| 문서화 담당(AI) | change/checks/review·확인된 사용자 결정 | 관련 문서, docs-update.md: 갱신·근거·남은 질문 | 허용된 문서·기록만 쓴다. 소스·테스트·승인·검토 판정을 바꾸지 않는다. |
| 개인 | AI의 계획·질문·검토 결과 | 중요 결정과 최종 채택·보류 | 프로젝트 범위·비용·자료 사용 등 권한이 필요한 선택을 확정한다. |

## 검사 실패와 중단

최초 검사 실패 뒤 원인을 확인하고 **추가 수정은 최대 2회**만 한다. 각 수정 뒤 같은 관련 검사를 다시 실행한다. 두 번째 추가 수정 뒤에도 실패하면 더 수정하지 않고 실패 명령, 관찰 결과, 추정 원인, 영향, 다음 조치를 기록해 개인에게 보고하고 중단한다. 새 범위나 중요 결정이 필요하면 먼저 개인에게 확인한다.

검증 실패는 원래 작성자에게 돌리고, 필수 검사가 통과·유효한 재사용으로 확인되기 전에는 최종 통과 검토로 넘기지 않는다. 필요한 검사가 미실행이면 통과가 아니라 보류다. 검토의 코드 결함은 작성자에게, 요구·범위·중요 결정의 불일치는 계획 담당과 개인에게 돌린다. 검증과 검토에서 발생한 수리는 같은 작업의 누계로 세며 역할·세션·회차 이름을 바꿔 초기화하지 않는다.

수정 후에는 바뀐 부분과 영향 인터페이스만 재검증하고 정확 후보에 필요한 새 검토를 받는다. 조건부 판정 중 필수 수정이 남으면 완료가 아니다. 문서화는 보류·실패 기록도 남길 수 있지만 통과로 바꾸지는 못한다. 단순 결과 기록·링크 정리는 해당 문서 확인으로 끝내며, 완료 기준·권한·인계를 바꾸는 문서 수정은 계획 및 영향 검증·독립 검토를 다시 거친다.

`AGENTS.md`와 이 문서는 작업 절차를 설명한다. **규칙 파일만으로 도구 권한, 파일 접근, 결제 또는 외부 서비스 사용이 기술적으로 강제되지는 않는다.** 실제 권한은 실행 환경과 도구 설정에 따르며, 개인 확인이 필요한 결정을 우회하는 근거로 문서를 사용하지 않는다.

파트가 완성되면 관련 검사를 묶어 실행한다. 유효한 통과 근거는 source·입력·환경·의존성·인터페이스·종료/정리가 같은 동안 재사용으로 표시한다. 변경과 새 실패가 없으면 전체 테스트·렌더·검토를 반복하지 않는다. 검증 서버·임시 출력의 소유권과 종료·정리를 기록하고, 최종 자료와 필요한 증거만 보존한다. 전체 폴더를 루틴 복사하지 않는다.
