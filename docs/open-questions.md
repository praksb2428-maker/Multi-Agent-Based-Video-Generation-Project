## 1. 제안서 원본

**질문:** 현재 `Video_Production_Project.md`를 이번 작업의 제안서 원본으로 확정할까?

- **A · 이 파일을 원본으로 확정 (추천):** 현재 브리프의 근거와 일치하며 곧바로 다음 단계를 진행할 수 있다. 단점은 별도의 최신 `proposal.md`가 있다면 그 차이를 놓칠 수 있다는 점이다.
- **B · 다른 `proposal.md`를 제공:** 최신 요구사항을 기준으로 문서를 고칠 수 있다. 단점은 파일을 받은 뒤 브리프를 재검토해야 한다는 점이다.

**추천 이유:** 저장소의 `README.md`와 `requirements.md`도 `Video_Production_Project.md`를 원 기획안으로 지목한다.

## 2. Python 의존성 관리 도구

**질문:** Python 3.12 가상환경에서 의존성을 어떤 도구로 고정할까? 제안서는 라이브러리 이름을 정했지만 설치·잠금 도구는 정하지 않았다([§4.3](../Video_Production_Project.md#L47)).

- **A · `venv` + `pip` + 명시적 의존성 파일 (추천):** 현재 표준 라이브러리 기반 코드와 제안서의 가상환경 계획에 가장 적은 변경으로 맞는다. 단점은 재현성을 위해 버전 고정과 갱신 절차를 직접 관리해야 한다는 점이다.
- **B · `uv` + 잠금 파일:** 설치와 잠금 절차를 한 도구로 묶을 수 있다. 단점은 팀과 실행 환경에 새 도구를 요구한다는 점이다.

**추천 이유:** 초기 하네스는 기존 Python 코드·테스트를 유지하며 시작하는 편이 단순하다.

## 3. 에이전트 실행 프레임워크

**질문:** 하네스가 처음부터 CrewAI를 전제로 할까, 아니면 프레임워크 선택을 뒤로 미룰까? 제안서는 CrewAI를 시험 후 확정할 **후보**로만 적었다([§4.2](../Video_Production_Project.md#L42)).

- **A · JSON 계약·승인 상태만 먼저 고정하고 프레임워크는 보류 (추천):** 현재 오프라인 기획 단계를 그대로 검증할 수 있고 후보 교체가 쉽다. 단점은 CrewAI 고유 통합을 나중에 시험해야 한다는 점이다.
- **B · CrewAI를 채택해 초기 하네스에 포함:** 제안된 역할 분리 흐름을 빨리 시험할 수 있다. 단점은 패키지와 실행 방식이 확정되기 전에 결합될 수 있다는 점이다.

**추천 이유:** 제안서가 승인 후 재개·JSON 전달·외부 도구 호출을 검증한 뒤 프레임워크를 확정하라고 한다.

## 4. 개발·검증 데이터

**질문:** 초기 테스트에 실제 주제·참고 자료·음성/영상 데이터를 사용할까? 제안서는 참고 자료를 선택 사항으로 두고 출처와 사용 가능 범위를 요구하지만 구체적인 자료는 지정하지 않았다([§3.2](../Video_Production_Project.md#L28), [§3.3](../Video_Production_Project.md#L32)).

- **A · 합성·공개 예제만 사용 (추천):** 개인정보와 자료 사용권 확인 없이 오프라인 검증을 시작할 수 있다. 단점은 실제 콘텐츠의 예외를 나중에 확인해야 한다는 점이다.
- **B · 사용권이 확인된 실제 자료 사용:** 실제 입력 특성을 일찍 검증할 수 있다. 단점은 사용 범위, 개인정보, 저장·삭제 기준을 먼저 정해야 한다는 점이다.

**추천 이유:** 초기 하네스의 JSON·승인 흐름은 합성 예제로도 확인할 수 있다.

## 5. 외부 API와 유료 검증 시점

**질문:** 초기 하네스에서 OpenAI/영상 생성 API의 실제 호출까지 준비할까, 아니면 오프라인 검증으로 멈출까? 제안서는 OpenAI 사용을 계획하지만 영상 API와 구체적 예산은 미정이며 제작 전 예상 비용·최대 예산 확인을 요구한다([§4.1](../Video_Production_Project.md#L38), [§4.1 예상 비용](../Video_Production_Project.md#L39)).

- **A · 우선 오프라인 검증, 유료 호출은 별도 결정 (추천):** 키와 결제 없이 기존 단계 및 파일 계약을 검증할 수 있다. 단점은 실제 API 호환성 확인이 늦어진다.
- **B · 승인된 예산 안에서 실제 API 연결 시험까지 준비:** 응답 형식과 비용을 일찍 확인할 수 있다. 단점은 제공자·모델·호출별 비용 상한·키 보관·전송 데이터 범위를 먼저 확정해야 한다.

**추천 이유:** 영상 제공자와 비용이 정해지지 않았고, 현재 코드에는 실제 비용 산정이나 제작 승인 단계가 없다. B를 고르면 제공자·모델, 한도, 키 주입 방식과 자료 전송 허용 범위를 후속으로 구체화해야 한다.
