- 실물 CLI: 보존된 A/B 합성 입력에서 새 모의 견적·승인을 만들고 `produce-mock → validate-result-mock`를 실행했다. 30초·360×640·24fps·720프레임, SRT/장면/hash, 원본/출력 보존을 확인했다. 기존 30초 산출물은 수리 2에서 제품 코드·입력·환경이 바뀌지 않았으므로 재렌더하지 않고 유효 증거로 재사용했다.
- 근거: Git 제외 `workspace/mock-media-20261030/`의 최초/수리 로그·CLI 로그·`verify_cli.py`, `result-30s/`, 시작/중간/끝 PNG. 대표 화면은 부모 검토 대상으로 넘긴다. native player의 전체 재생·실제 AI 내용/인물 일관성·말소리 동기화는 미검증/합성에 해당하지 않는다. 보고의 사람 확인 상태는 pending이다.

## 결과 검사보고와 수정 요청

2026-10-30, Python 3.12.1·FFmpeg/FFprobe 9.0.1에서 파일 닫기 경고 회귀를 추가한 70개가 통과했다. MP4 헤더를 `with`로 읽고 실제 결과 검사와 GC 후 `ResourceWarning`이 없는지 확인했다. 기존 D 수리 2/2 이력은 유지하며 이번 경고 수정은 사용자의 명시적 후속 요청으로 별도 기록한다.

E 기능 최초 검사는 80개가 통과했다. 필수 환경 센티널 보완을 E 수리 1/2(검증 환경 보완, 제품 수정 0)로 기록한다. 최종 후보에서 `.venv\Scripts\python.exe -X utf8 -W always::ResourceWarning -m unittest discover -s tests -v`를 새로 실행해 80개가 20.781초에 통과했고 ResourceWarning은 0이었다. 키/프록시 환경을 전체 복사하지 않고 PATH/PATHEXT/SystemRoot/WINDIR만 허용했다. OPENAI_API_KEY·HTTPS_PROXY 조회와 DNS·소켓 접근 패치가 실제로 거부하는지 assertion으로 확인한 뒤 검사→확인→재검증을 실행했다. OS 방화벽 격리 주장은 하지 않는다.

- E1: 기술 검사 성공/실패를 별도 보고로 저장한다. 단계별 오류 경계와 고정 행동 ID를 검사하고 알 수 없는 오류는 수동 확인으로 막는다. 누락 결과·입력/승인 오류는 성공으로 기록하지 않는다.
- E2: 명시적 accept/request_changes, 네 분류의 수정 요청, 유효 장면 번호, 필수 설명·버전·타입을 검사한다. 기술 실패 accept, 빈 수정 요청, 실행 플래그·알 수 없는 키, null/NaN/중복 키는 거부한다.
- E3: 입력·결과·보고·확인 기록·경로 변경, digest를 다시 쓴 상태/후속 경로 변조, 오래된 연결과 잘못된 UTC 시각을 거부한다. 저장 재검증에서도 실제 기술 검사를 반복한다. 실패 보고의 수정 요청은 허용하되 기술 실패 상태를 유지한다.
- E4 실물 CLI: 기존 30초 결과를 재렌더 없이 검사하고 예제의 합성 accept/changes 기록을 각각 저장·재검증했다. 손상된 복사본은 실패 보고를 남기고 accept를 거부했다. 기존 출력 덮어쓰기를 거부하고 여섯 입력과 다섯 원본 결과의 SHA-256 불변을 확인했다. 원 제작 증거는 기존 실행 ID 그대로 재사용하며 이번 재검사는 새 실행이다.

근거는 Git 제외 `workspace/quality-feedback-20261030/`의 `warning-fix-tests.log`, `e-initial-tests.log`, `e-coverage-tests.log`, `verify_cli.py`, `cli-summary.log`, 검사·확인 JSON 및 원본 해시다. 중간 `e-final-tests.log`는 환경 보완 중의 80개 기록이며 최종 정의 증거는 `e-coverage-tests.log`다. 모델 용량 인프라 실패 1회와 동일 설정 재시도는 제품 실패·수리와 구분한다. 실제 API/키/유료 호출·AI 영상/TTS·네이티브 플레이어 전체 재생·실사용자 시청/채택은 실행하지 않았다. 합성 검토자 표기는 사용자 수락 증거가 아니고 기존 `quality.json` 사람 확인은 pending이다. 독립 검토는 별도다.

## 수정 요청과 별도 재승인 모의 재제작

2026-10-30 Python3.12.1·FFmpeg/FFprobe9.0.1에서 `.venv\Scripts\python.exe -X utf8 -W always::ResourceWarning -m unittest discover -s tests -v`를 실행했다. 기존82개+신규8개, **90개가 30.952초에 첫 검사 통과**, ResourceWarning0. F 수리0/2이며 E2/2, D2/2와 명시 warning 수정, A/B/C0/2, SDK2/2+null예외1/1 이력을 보존한다. capacity 인프라 재개1은 제품 수리와 구분한다.

- F1: 수정 요청→명시 patch→미승인 draft, 기획 재승인 전 준비 거부, 새 견적 후 제작 승인 대기를 확인했다. 통합 함수는 승인 함수를 호출하지 않는다.
- F2/F3: 누락·원본·만료·실제 실행 플래그의 모의 승인, 다른 재승인 기획, 변조된 source/inspection/review/명시 patch를 거부했다. 잘못된 새 승인은 도구 실행·폴더 생성 전에 거부한다. 현재 원본 미디어 QA는 읽기 전용으로 계속 재검사한다.
- F4/F5/F6: accepted/원인 불명 수동 확인 상태, 재해시한 handoff의 버전·실행 플래그·계보, saved draft/patch, prepared prompt/quote/pricing 변경과 덮어쓰기·workspace 밖·상위 이동을 거부했다. 고정 파일만 읽고 manifest의 임의 경로를 따라가지 않는다. 실제 OS symlink/junction 생성은 F에서 별도로 실행하지 않았으며 기존 경로 검사를 재사용한다.

## 후속 구현 시 검사할 범위

E 독립 검토에서 손상 MP4의 FFprobe 진단문에 포함된 프로세스 주소가 달라져 동일 결과의 수정 요청도 stale로 거부되는 결함을 확인했다. E 수리 2/2는 원본 진단문을 보고·해시에 계속 보존하면서 현재성 비교에서만 제외한다. 실패 필드의 정확한 구조·문자열, check_id·상태·후속 경로·입력·결과 snapshot은 계속 검증한다. 최종 전체 82개(기존 80+회귀 2개)가 20.140초에 통과했고 ResourceWarning은 0이었다. 실제 손상 복사본에서 검사→명시적 수정 요청→저장 재검증, 실패 accept 거부와 기존 확인 기록 호환성을 확인했다. 원본 11개 SHA는 불변이다. 근거는 `workspace/quality-feedback-20261030/repair2-tests.log`, `repair2-cli-summary.log`, `repair2/`다. E 누계 2/2(검증 환경 보완 1+제품 수정 1)로 소진했으며 이전 검토 실패와 증거는 보존한다.

| 대상 | 전략 | 상태 |

초기 데이터는 [확정 ADR](decisions/0004-synthetic-data.md)에 따라 합성·공개 예제만 사용한다. 실제 참고 자료, 개인정보, 음성·초상 또는 외부 서비스가 필요한 검사는 해당 결정과 사용 범위를 먼저 확정한다. 지금은 전체 제작·미디어 검사용 명령이 **미구성**이며 성공 여부를 주장하지 않는다.
